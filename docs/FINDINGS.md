# Что выяснилось в процессе

Всё ниже — результат многочасовой отладки на живой станции. Если вы застряли на одном из
этапов, скорее всего ответ здесь.

## 1. Почему MITM перестаёт работать через пару минут

Классическая картина при попытке включить ADB через подмену `quasar.yandex.net`:

- сразу после сброса станция **принимает** поддельный сертификат и забирает конфиг;
- через 1–3 минуты — `SSL_do_handshake() failed ... tlsv1 alert unknown ca`.

Причина не в прошивке (номер версии не меняется), а в том, что станция **самостоятельно
обновляет хранилище доверенных корней**:

```
/system/vendor/quasar/ca-certificates.crt -> certs/ca-certificates.crt
```

Файл успевает обновиться раньше, чем вы успеваете что-то сделать. Отсюда правило: **окно
доверия ≈ 1–2 минуты после сброса**, и всё надо делать в нём.

Проверить, что именно происходит, можно по логам nginx (если используете свой):

```
SSL_do_handshake() failed (SSL: error:0A000418:SSL routines::tlsv1 alert unknown ca)
```

## 2. Заводская прошивка 0.18.1 не умеет adbd

Заводской образ (`0.18.1.23...20230810.factory`) доверяет CA, но **не активирует ADB** по
конфигу — ключ `system_config.adbd` в нём просто не обрабатывается. Нужна прошивка
`0.369.1.46+`.

Отсюда трюк из `yandex-station-root`: после сброса станции подсовывается **один** апдейт `.46`
через поддельный `update_manifest.json` (ZIP качается с настоящего CDN Яндекса), после чего
активация проходит.

## 3. `.50` отвергает CA-цепочку

Сборка `0.369.1.50...` (и новее) не доверяет eMudhra. Поэтому:
- либо остаётесь на `.46`,
- либо ставите ADB-гард **до** обновления — он переживёт переезд на `.50`.

Гард — это подмена `/system/vendor/quasar/activate_adb.sh` обёрткой, которая игнорирует
`deactivate` и заново поднимает сетевой ADB. Оригинал сохраняется рядом как
`activate_adb.root_original.sh`.

## 4. musl и ядро 4.9: падение по clock_gettime64

Если собрать бинарник статически на musl (Alpine), он **падает** на этой станции:

```
shairport-sync[2540]: syscall 403
unhandled level 3 translation fault (11)
```

`syscall 403` на arm32 — это `clock_gettime64`, появившийся в ядре 5.1. Здесь ядро **4.9**.

`-D_TIME_BITS=32` помогает не всегда (зависит от того, как передаются флаги в подпроекты).

**Решение:** собирать под старый glibc (Debian buster, glibc 2.28). На станции glibc 2.30,
libstdc++ 6.0.28 и libgcc_s есть — бинарник заводится без дополнительных библиотек.

Заодно: статически линкуйте только отсутствующие библиотеки (`libconfig`, `libpopt`), а
`libasound`/`libssl`/`libc` — динамически, они на устройстве есть.

## 5. `mediad` монопольно держит ALSA

Любой приёмник (AirPlay, Spotify Connect) упрётся в:

```
The output device "plughw:0,0" is busy
```

Держит его `/system/vendor/quasar/maind --mediad`. В карте **один субпоток**, dmix не
используется (`/dev/shm` пуст), так что разделить устройство нельзя.

Но: если `mediad` убить, он **перезапускается сам** и устройство больше не захватывает, пока
ему не понадобится. Этого достаточно.

```sh
# /etc/airplay-free.sh
for p in $(ps -o pid,args | grep -F "maind --mediad" | grep -v grep | cut -d" " -f1); do
  kill -9 "$p" 2>/dev/null
done
```

Вызывать: при загрузке (с задержкой ~30 с) и по хукам плеера
(`run_this_before_entering_active_state`).

Цена: пока играет AirPlay/Spotify, Алиса не сможет говорить. Это осознанный размен.

## 6. Обновления отключаются в launch.json

```
/system/vendor/quasar/launch.json
```

Убрать задачу `updatesd` — и OTA больше не запускается. Проверка:

```sh
grep -c updatesd /system/vendor/quasar/launch.json   # 0
```

Учтите: установщик `yandex-station-root` при отключении обновлений пытается перемонтировать
`/` в rw и падает с `mount: ... Device or resource busy`, **уже после** записи файла. Ошибку
можно игнорировать, но проверяйте результат.

## 7. Мелочи, на которые уходит время

- **`/data/local/tmp` не существует** — `mktemp` падает с `No such file or directory`.
  Перед установкой: `adb shell mkdir -p /data/local/tmp`.
- **`/` обычно смонтирован read-only.** Перед записью: `mount -o remount,rw /`.
  Обратно — `mount -o remount,ro /` (не обязательно, при перезагрузке вернётся само).
- **busybox без `nohup`** на OpenWrt: демоны запускать через `start-stop-daemon -S -b -x`.
- **`init 6` не работает** (не PID 1) — перезагружать через `reboot`.
- **DNS-подмену нельзя делать глобальной** на роутере: телефон с приложением «Дом с Алисой»
  ходит на те же домены и получает заглушечный конфиг → «нет списка устройств».
  Подменяйте только для MAC станции, а остальное — через DNAT по её адресу.
- **Станция кеширует IP** и иногда ходит на настоящий адрес Яндекса мимо вашего DNS.
  Надёжнее завернуть её трафик на прокси через `dnat`/`redirect` по MAC.
- **QUIC (UDP 443)** капризен: если перехватываете только TCP, станция может обновиться по
  QUIC незаметно для вас.

## 8. Сборка Rust-бинарников в Debian buster

`rustup` в buster **не работает**: устаревшие корневые сертификаты, curl внутри rustup падает с
`SSL certificate problem`. Обход — ставить Rust напрямую из дистрибутива:

```sh
curl -kfsSL -o rust.tar.gz \
  https://static.rust-lang.org/dist/rust-1.75.0-armv7-unknown-linux-gnueabihf.tar.gz
tar xzf rust.tar.gz && cd rust-1.75.0-armv7-unknown-linux-gnueabihf
./install.sh --prefix=/usr/local --disable-ldconfig
export PATH=/usr/local/bin:$PATH
```

То же касается любого `curl` внутри buster — добавляйте `-k` или обновляйте `ca-certificates`.

## 9. Spotify Connect не работает: Spotify не отдаёт аудио третьим клиентам

Проверено на двух клиентах — `spotifyd 0.4.1` (librespot 0.4) и `librespot 0.6.0`, собранном
вручную. В обоих случаях:

```
ERROR librespot_playback::player] Track should be available, but no alternatives found.
WARN  librespot_playback::player] <spotify:track:...> is not available
```

В метаданных трека при этом:

```
file: []
alternative: []
restriction: []        # ограничений по стране нет
availability: []
```

То есть Spotify возвращает трек **без единого аудиофайла**. Проверено:

- аккаунт **Premium** (`"type": "premium"`, `"financial-product": "pr:premium,..."`);
- страна аккаунта `SG`, но `restriction` пустой — не гео-ограничение;
- разные битрейты (96/160/320) — без разницы;
- OAuth-авторизация проходит, AP-соединение устанавливается, устройство видно в Spotify.

Причина — политика Spotify: их сервер не выдаёт аудио неофициальным клиентам, даже при
Premium. Обходится только своими `client_id`/`client_secret` (что не даёт права на streaming)
или отказом от сторонних клиентов.

**Рабочий путь для Spotify на станции — AirPlay.** Приложение Spotify умеет выводить звук на
AirPlay-приёмник, а `shairport-sync` на станции играет без проблем.

## 10. Проверено с librespot 0.8.0 и spotiya: audio key

`librespot 0.8.0` исправляет пустые метаданные (перешёл на extended-metadata), но дальше
упирается в ключи:

```
[ERROR librespot_core::audio_key] error audio key 0 1
[WARN  librespot_playback::player] Unable to load key, continuing without decryption
[WARN  librespot_core::dealer] Websocket connection failed: peer closed connection without
      sending TLS close_notify
```

Это открытый баг librespot [#1649](https://github.com/librespot-org/librespot/issues/1649),
затрагивающий 0.7.0+. Воспроизводится и на `spotiya 0.7.1` (обёртка над librespot 0.8.0,
сделанная специально под Мини 2).

Что проверено и исключено:

- аккаунт Premium, `"explicit-content": "1"`, `"streaming": "1"` — не фильтры;
- разные битрейты (96/160/320);
- разные шлюзы (блокировка `ap-gew1.spotify.com` через DNS);
- маршрутизация трафика станции через прокси/VPN на роутере (вместо прямого выхода);
- полная перезагрузка станции.

Ошибка воспроизводится стабильно, то есть это серверная политика Spotify по отношению к
клиенту, а не проблема сборки.

**Вывод: Spotify Connect на станции сейчас не работает.** Рабочая альтернатива — AirPlay
(приложение Spotify умеет выводить звук на AirPlay-приёмник).

`spotiya` при этом остаётся лучшим кандидатом: он сделан именно под Мини 2 (кнопки, дисплей,
голосовое управление), и как только Spotify перестанет упираться — заработает как есть.

## 11. Окончательный диагноз: аудиоключи зависят от аккаунта

После перехода на `librespot 0.8.0` (и `spotiya 0.7.1`, который его использует) метаданные
приходят с файлами, но Spotify отказывает в аудиоключе:

```
[ERROR librespot_core::audio_key] error audio key 0 1
```

`0 1` — это два байта ответа шлюза (`data[0]=0x00`, `data[1]=0x01`), см.
`core/src/audio_key.rs`. То есть отказ приходит от сервера.

**Это свойство аккаунта, а не устройства.** Подтверждение — issue
[#1735](https://github.com/librespot-org/librespot/issues/1735): на одной машине, одном
бинарнике, одном шлюзе один Premium-аккаунт играет, другой получает ту же ошибку на всех
треках. Есть и
[PR #1763](https://github.com/librespot-org/librespot/pull/1763) (на момент проверки не влит),
который делает ретраи — но у нас ретраи через `spotiya --retry` результата не дали.

Исключено по ходу проверки:

- подписка (Premium, `"streaming": "1"`, `"explicit-content": "1"`);
- страна и каталог (`restriction: []`, `availability: []`);
- битрейты 96/160/320;
- выбор шлюза (`gew1`/`gue1`/`gew4`, в т.ч. блокировка `gew1` через DNS);
- маршрутизация станции через VPN на роутере;
- системное время (сверено с NTP, совпадает);
- перезагрузки и повторные входы по OAuth.

Почему «у людей в тиктоке работает»: официальные клиенты (и приложения на Web Playback SDK)
Spotify не блокирует — там другой путь получения аудио. `librespot` использует устаревший
Mercury-запрос AES-ключа, и для части аккаунтов Spotify его отклоняет.

**Итог:** для таких аккаунтов Spotify Connect на колонке невозможен. Рабочий путь —
AirPlay (Spotify умеет выводить на него звук).

## 12. Индикатор Мини 2 можно забрать себе

Дисплей — не матрица, а **4-разрядный 7-сегментный индикатор**: 34 белых светодиода
(`mini2:white:clockA1..G4`, `DEGREE`, `MINUS`, `PLUS1..4`) плюс RGB-кольцо из 6 сегментов
(`mini2:{red,green,blue}:ring1..6`). Всё это обычные записи в
`/sys/class/leds/<led>/brightness` (0..255).

Главный подвох: белые светодиоды постоянно трогает `maind --platformd`. Убивать его бесполезно —
перезапускается за ~0.2 с. **Но обновляет он их дифференциально**: пишет только те сегменты,
чей символ изменился. Поэтому если перерисовывать свою картинку чаще, чем меняется время
(раз в секунду), картинка остаётся вашей, а штатный демон продолжает работать — кнопки,
кольцо на громкость и всё остальное не ломается.

RGB-кольцо при этом вообще не перерисовывается: выставили цвет — он держится.

Откат — убить свой процесс и перезагрузиться, штатные часы вернутся сами.

### Почему анимация на цифрах не получается

Проверено на живой колонке: `maind --platformd` возвращает свои значения **меньше чем за 20 мс**,
то есть перерисовывает индикатор быстрее 50 Гц. Из shell это не обогнать: любые свои значения
сразу заменяются штатными, на индикаторе всегда часы. Файл `files/etc/statusd.sh` оставлен как
эксперимент и **не работает** — включать его смысла нет.

Если очень нужна своя картинка, единственный путь — убрать `platformd` совсем (правка
`launch.json`/`quasar.cfg`), но тогда пропадает штатная световая реакция на кнопки, громкость
и «Алису». Это уже вмешательство в прошивку, а не надстройка над ней.

Кольцо (`mini2:*:ring*`) при этом штатный демон не перерисовывает — выставленный цвет держится.
Но трогать его смысла мало: при любом событии (громкость, «Алиса») прошивка вернёт своё.
